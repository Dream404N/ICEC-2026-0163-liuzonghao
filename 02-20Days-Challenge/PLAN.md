# 项目四执行计划 · 校园节点雷达

> 起跑 2026-11-10，封仓 2026-11-24。全部运行在 GitHub Actions，本机零常驻、零自启。

## 一句话

机器每 30 分钟自己去看一眼学校与考试网站，看到「哪天之前要做什么」就写进一份日历订阅；同时把「自己真的看过」逐条记成日志，并用哈希链让日志改不动。

## 为什么是这个方向

项目四要的是「解决校园真实痛点的轻量化实用程序 + 连续不少于 7 天自动化运行日志」。多数校园痛点长在人的设备和账号里（微信、学习通、课表），云端机器摸不到；能无人值守反复执行、且每天都会变的，只有**公开信息本身**。

同期选择项目四的四位同学做的是课表邮件提醒、生活费记账、校园 WiFi 地图，都属用户端工具。本方案把技术含量放在「交付物可自证」，不与他们正面撞车。

## 评分点对照

| 评分项 | 对应交付 |
|---|---|
| 连续 ≥7 天 telemetry 日志（含时间戳、频次、耗时、报错） | `process_logs/YYYY-MM-DD.jsonl`，每轮一条，脱敏到分钟 |
| 基于日志做 3 次 Git 迭代 diff | `iterations/`，每次由真实故障或指标变化触发，附前后对比 |
| 源码 + 8 位真实用户反馈 | `src/`、`public/calendar.ics`、`feedback/` |
| Git 证据链与复盘 | 每日 `*.summary.json` + Merkle root 写入 commit message + `verify.py` |

## 时间线

| 日期 | 动作 |
|---|---|
| 11-10 | 最小轮次上线，Actions 起跑；首轮建立基线（现有公告只收录，不计「新增」） |
| 11-11 ~ 11-12 | 观察真实失败：页面改版、超时、限流、编码差异；日志如实留痕 |
| 11-13 | **迭代 #1**：按日志里的失败类型修解析器或重试策略，commit diff 附前后成功率 |
| 11-14 ~ 11-15 | 上线确定性截止日抽取规则 + 人工标注真值评测集，统计准确率 |
| 11-16 | **迭代 #2**：按评测集补规则，diff 附准确率变化；发放 `.ics` 给 8 位同学 |
| 11-17 | 7 天主窗口完成；收反馈 |
| 11-18 | **迭代 #3**：按真实反馈调整提醒粒度或展示，diff 附反馈原文编号 |
| 11-19 ~ 11-20 | 脱敏核查、`verify.py` 全链校验、报告撰写；仓库转公开 |
| 11-21 ~ 11-23 | 面试准备：把每个评分点对应到具体 commit 与日志行 |
| 11-24 | 封仓 |

三次迭代是**由日志触发**，不是预先排好的剧本。若某类故障没发生，就按实际发生的那类写，不编造。

## 8 位同学反馈怎么收

把 `public/calendar.ics` 发给他们导入手机日历（Android / iOS / Windows / Linux 原生支持，无需安装任何软件）。只问三个问题：有没有漏掉该提醒的事、有没有误报、提醒提前多久合适。收截图或一句话原话，编号归档到 `feedback/`，不收集姓名、学号、手机号。

## 明确不做

- 不读微信本地数据库、不逆向学习通、不登录任何需要身份的页面；
- 不在本机跑常驻进程、不写自启、不建定时任务；
- 不补写历史日志，缺勤轮次由 `verify.py` 如实报出；
- 不用演示数据冒充真实日志。本目录 `preview.html` 是版式样张，已醒目标注示例数据，与 `public/index.html` 的真实数据严格分开。
