# 迭代 011 · 提交文案把「累计」写成了「当日」

**触发证据（远端提交信息 vs 实际文件行数）**

| 远端 commit | 提交信息 | 对应文件 | 实际行数 |
|---|---|---|---|
| `596d7e57` | 课序运行日志 2026-11-16（真实事件 **40** 条） | `2026-11-16.jsonl` | 34 |
| `fb308175` | 课序运行日志 2026-11-17（真实事件 **71** 条） | `2026-11-17.jsonl` | 31 |
| `83521160` | 课序运行日志 2026-11-18（真实事件 **77** 条） | `2026-11-18.jsonl` | 6 |
| `698b2932` | 课序运行日志 2026-11-19（真实事件 **103** 条） | `2026-11-19.jsonl` | 26 |
| `3f4e59bf` | 课序运行日志 2026-11-20（真实事件 **114** 条） | `2026-11-20.jsonl` | 11 |

差异不是随机的。把各分片行数累加：

```text
6（11-15）+34 = 40 ✓ 11-16
           +31 = 71 ✓ 11-17
           +6  = 77 ✓ 11-18
           +26 = 103 ✓ 11-19
           +11 = 114 ✓ 11-20
```

五条全部吻合，说明 `total` 是**所有分片的累计行数**，不是当日条数。

## 判断：数字没造假，但表述会被读成虚报

每一行都是真实事件，没有一条是编的——这一点必须先说清。
问题在于提交信息写成「2026-11-20（真实事件 114 条）」，任何人都会读成
「20 号这天产生了 114 条事件」，然后打开文件只看到 11 行。
在「不造假」是硬条件的评审里，**这种可复现的落差比数字本身危险得多**：
它不需要评委怀疑数据，只需要评委数一下行数。

代码位置 `electron/log-sync.cjs`：

```js
let total = 0;
for (const f of files) total += f.content.toString('utf8').split('\n').filter(Boolean).length;
const message = '课序运行日志 ' + beijingDate(this.now()) + '（真实事件 ' + total + ' 条，' + reason + '）';
```

## 这次实际改了什么

```js
// 口径修正（0.1.5）：total 是所有分片的累计行数，不是当日条数。
const today = beijingDate(this.now());
let total = 0;
let todayCount = 0;
for (const f of files) {
  const lines = f.content.toString('utf8').split('\n').filter(Boolean).length;
  total += lines;
  if (f.name === today + '.jsonl') todayCount = lines;
}
const message = '课序运行日志 ' + today + '（当日 ' + todayCount + ' 条 / 累计 ' + total + ' 条，' + reason + '）';
```

当日与累计拆开写，两个数字都对得上文件，也不需要读者自己反推。

## 这次改动的边界

- **已发布的历史提交信息不重写**。改写 Git 历史会让「日志链可验真」这件事本身失效，
  代价远大于收益；这里选择公开勘误，而不是把痕迹抹掉。
- **运行中的 0.1.4 安装包仍是旧文案**。源码与单测已修，但 asar 内嵌在 exe 里、
  带 integrity 校验，重新打包并覆盖安装是一次独立发版动作；在封仓前不重启这条链路，
  所以**下一次自动提交（11-21 23:50）仍会写「真实事件 N 条」**，0.1.5 打包后才生效。
- `tools/kexu/source/log-sync.cjs` 是 0.1.4 的历史快照，**保持原样不覆盖**，
  以免快照与实际发版失真；新口径以 `tools/kexu/app/` 为准。
