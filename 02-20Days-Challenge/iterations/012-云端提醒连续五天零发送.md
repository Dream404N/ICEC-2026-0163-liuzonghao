## 归因：不是没课，是定时器到得太晚，脚本直接退出

抓取 11-17 最后一次运行的原始步骤输出，脚本只打印了一行：

```json
{"date": "2026-11-17", "action": "no_period_now", "note": "当前时刻不在任何提醒点 ±15 分钟内，也未传 --period"}
```

紧接着的提交步骤回显「无新增日志」。原因分两层：

**第一层，cron 排队。** GitHub 免费 runner 的高峰期延迟远不止文档说的「几分钟」：

| 计划（UTC） | 11-16 实际到达 | 迟到 | 11-20 实际到达 | 迟到 |
|---|---|---|---|---|
| 00:20（P1） | 01:34:48 | +74 分 | 01:19:42 | +59 分 |
| 02:00（P2） | 02:50:36 | +50 分 | 02:47:50 | +47 分 |
| 05:10（P3） | 06:17:59 | +67 分 | 06:10:25 | +60 分 |
| 06:50（P4） | 09:25:38 | **+155 分** | 07:57:54 | +67 分 |

**第二层，脚本判定方式。** `run.py` 不传 `--period` 时调用 `pick_period()`，
只在「距离某个提醒点 ±15 分钟」内命中；命中不了就 `return`，
**既不写 `skipped_late`，也不写任何记录**。于是「迟到两小时」和「今天没课」
在日志里长得一模一样，都是什么都没有。

而 `run.py` 内部本来就有正确的迟到判定（`latency > tolerance` → `skipped_late`，
`now >= class_start` → `skipped_after_class`），只是根本没走到那里。

## 这次实际改了什么

`.github/workflows/prebell-remind.yml` 里，schedule 触发时按**本次是哪条 cron**
直接指定大节，不再让脚本猜当前钟点：

```yaml
case "${{ github.event.schedule }}" in
  "20 0 * * 1-5") PERIOD=P1 ;;
  "0 2 * * 1-5")  PERIOD=P2 ;;
  "10 5 * * 1-5") PERIOD=P3 ;;
  "50 6 * * 1-5") PERIOD=P4 ;;
esac
...
elif [ -n "$PERIOD" ]; then
  python prebell/run.py --period "$PERIOD" --source "$SRC"
```

改完后，无论 cron 什么时候被唤醒：

- 准点到 → 正常发提醒；
- 晚到但还没上课 → 走 `skipped_late`，**如实落盘、不发**（不补推）；
- 晚到已过上课时间 → 走 `skipped_after_class`，同样落盘、不发。

三种情况都会在 `process_logs/YYYY-MM-DD.jsonl` 里留下一条记录，
summary 的 `skipped_late` / `skipped_after_class` 也不再恒为 0。
