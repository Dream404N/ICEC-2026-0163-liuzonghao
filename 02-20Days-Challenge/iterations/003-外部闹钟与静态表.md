# 迭代 #003 · 定时搬出 GitHub，课表一次算完

> 2026-11-13。由使用者一句「没必要 课表又不是天天变 你这频率太高了」触发。
> 这次改的是**架构**，不是参数——旧方案的模式从一开始就选错了。
> 不修改任何已提交的历史记录，只新增说明。

## 上一个版本错在哪

旧方案是「课前窗口内每 5 分钟醒一次」：6 条 cron，工作日每天 14 次，一周 72 次。
每次醒来都完整跑一遍「现在第几周 → 下一大节是哪个 → 这周有没有课 → 要不要推」。

两个问题，第二个更根本：

1. **额度**。一周 72 轮，一个月约 288 分钟。占不满 2000 的额度，但白烧。
2. **模式错位**。课表是**一学期的常量**，不是天天变的数据。轮询是给动态数据准备的姿势；
   对静态数据轮询，等于每 5 分钟重新证明一遍同一个结论。而且每次重算都可能在悄悄分叉——
   算错了也不会有人知道，因为没有第二份结果可以对照。

再看一眼课表本身：

| 大节 | 开始 | 有课的日子 | 课前 20 分钟 |
|---|---|---|---|
| 第一大节 | 08:40 | 周一、周四 | 08:20 |
| 第二大节 | 10:20 | **整学期无课** | — |
| 第三大节 | 13:30 | 周一、周二、周三、周五 | 13:10 |
| 第四大节 | 15:10 | 周一、周二、周三、周四 | 14:50 |

整张表只用到 3 个大节。为这 3 个时刻，配了 6 条 cron 每天醒 14 次。

## 改法

### 一、定时搬出去

GitHub `schedule` 最小粒度 5 分钟、高峰期排队能晚十几分钟。这是它公开的缺陷，
不是脚本能修的——用「多重试几次」去补偿，本质是拿冗余掩盖工具选错。

改成 cron-job.org 到点用 `workflow_dispatch` 把大节号踢进来，GitHub 只当执行体：

```
cron-job.org（3 个 job，精确到分钟）
      ↓  POST workflow_dispatch，body 带 period=1/3/4
GitHub Actions（查表 → 推微信 → 写哈希链 → 出 .ics / 网页）
      ↓  POST 官方接口
Server酱 → 微信
```

| job | 北京 | cron（UTC） | 涵盖 |
|---|---|---|---|
| `period=1` | 08:20 | `20 0 * * 1,4` | 周一、周四 |
| `period=3` | 13:10 | `10 5 * * 1,2,3,5` | 周一、二、三、五 |
| `period=4` | 14:50 | `50 6 * * 1,2,3,4` | 周一、二、三、四 |

一周 10 次唤醒，一个月约 40 分钟（占免费额度 2%）。

**顺带捡到一个更好的证据**：cron-job.org 的执行历史会同时记录「计划时刻」和「实际执行时刻」
（保留最近 50 次）。旧日志里 `planned_slot_5m` 只能老实承认是「按实际时刻向下对齐的近似值」，
因为 GitHub 不暴露计划时刻；现在计划时刻有第三方独立留痕，比我们自己写的字段硬。

### 二、课表一次算完

新增 `src/resolve.py`，把 `timetable.json` 展开成**整学期 96 条推送**：

| 产物 | 内容 |
|---|---|
| `src/schedule.json` | 机器用：每条 `{date, week, period, class_start, push_at, courses[]}` |
| `src/schedule.md` | 人读：按周汇总 + 96 行明细 |
| `src/out/cron-hints.txt` | 闹钟用：由表反推的 3 条 cron（UTC / 北京双列） |

运行时 `prebell.py` 只查表。表里没有这一格，就是本周没课，记 `no_class_this_week` 不打扰。
课表改了重跑 `resolve.py`，`--check` 会告诉你表是否过期、cron 是否需要跟着改。

`verify.py` 的期望值也跟着改：从写死的 `PREBELL_WEEKDAY_ROUNDS = 12` 换成按 `schedule.json`
逐日推导——**该响几节、缺哪一节，直接点名**，例如 `2026-11-17: 该响没响 2026-11-17-P4`。

### 三、撤掉周末心跳

旧方案为了凑「连续 7 天日志」，给周六周日各配一条心跳：不推微信，只写一行空日志保链。

这是为了验收指标造记录。11-21、11-22 本来就没课，程序没理由在没事件发生时留痕。
撤掉之后 `verify.py` 的期望值是按课表算的，没课的日子期望为 0，不再判缺口。

## 这次没做的事，以及为什么

- **没删旧雷达的 `probe.yml`**：它还在跑到 11-17 满 7 天，日志是真实过程数据，不提前掐断。
- **没做「放假调休」跳过**：cron-job.org 只按星期触发，遇调休会照推。要做需要在
  `timetable.json` 加 `holidays` 字段，属于下一轮迭代，不在这次改架构的范围里。
- **没保留 GitHub 原生 `schedule` 做兜底**：双通道会让同一节课响两次，正是这次要消掉的毛病。
  代价是单点触发、一次踢空就漏一节课——写进文档，不假装没有。

## 代价，写在这里

- cron-job.org 免费、无 SLA，官方明说高峰期可能迟到。迟到多少记 `late_by_min`，
  超过 15 分钟记 `missed_too_late` 不发（课都上一半了，推了也是噪音）。
- GitHub token 存在第三方。缓解：fine-grained PAT 只给这一个仓库 `Actions: write`，
  读不了代码、改不了仓库；有效期设到学期末之后。
- 课表锚点（第 1 周 = 2026-09-07）仍是**估算**。整张表 96 条日期都由此推出，
  所以每条都带 `estimated: true`，等使用者校对后再改 `anchor.verified`。
