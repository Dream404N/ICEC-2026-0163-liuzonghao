## 二、主文案（998 字符，按使用者本人叙述整理，可直接粘贴）

> 这一版保留了使用者本人的判断与语气（「这个项目本身不复杂」），只做了两件事：
> 把 Linux 端删掉（仓库无实现痕迹），把「没有技术卡点」换成真实发生过的那个卡点。

```
做了一套课前自动提醒工具，最终形态是 Windows 客户端「课序」：托盘常驻，到点右下角弹提醒，
课表存在本机、不联网也能用。有安卓端（Capacitor），Windows 与安卓共用同一份课表。

方案换过好几轮，都是被实际使用否掉的：最早用 GitHub Actions 定时推送，后来废弃——
免费 cron 排队延迟实测 47 到 155 分钟，国外 runner 也不稳定，课前提醒迟到半小时就没意义。
也想过推微信，但微信没有官方 Bot 接口、只有企业微信有；退一步用 Server 酱走公众号仍不行，
公众号消息得点进去才看得到，不适合「马上要上课」这种即时提醒。
最后转向本地优先：客户端自己算时间、自己弹窗，不依赖服务器。

技术上有两处不好绕：一是提醒时钟——云端 cron 靠不住，本地就得自己保证到点触发，
Windows 的通知权限、免打扰、休眠唤醒都要处理（日志里 system_resume 专记唤醒）；
二是数据留存——APK 每次构建换签名就得卸载重装，一卸载连数据一起删，所以固定了签名。

最大的排障复盘其实是个「假绿」：云端提醒连续 5 天出问题，但 GitHub Actions 显示
20 次 schedule 全部 success。翻 process_logs 才发现 attempted=0、sent=0，
一条消息都没发出。原因不是代码写错，而是 cron 迟到 47 到 155 分钟，
脚本的时间窗口判断只在前后 15 分钟内生效，晚了就直接退出、连日志都不落——
失败被静默吞掉了。改法是让 cron 显式传大节编号，迟到就判 skipped_late 并如实落盘。
教训比代码重要：success 不等于做成了事，日志里没有的，就是没发生。

如实说明：这个项目本身不复杂，难点不在算法，在「让它在真实环境里每天可靠地跑」。
还有两处没闭环：校历第 1 周按 2026-09-07 推算，未取得官方周历无法确认，已在页面标注为已知前提；
那处 cron 修复也还没被真实 cron 验证，周一早上才有第一次机会。

可核对指标：连续 7 天运行日志（11-16~11-22，123 条真实事件，客户端每天 23:50 自提交，
关机就空着不补写）；基于日志迭代 12 篇，3 篇修的是真缺陷；源码 123 文件；
课程提醒真实送达 4 次（另 2 次为功能测试）；真实用户反馈 8 份。
```
