## 二、主文案（913 字符，含换行；直接粘贴不超 1000 上限）

```
做了一套课前自动提醒工具，最终形态是 Windows 客户端「课序」：托盘常驻，到点右下角弹提醒，
课表存在本机、不联网也能用。同源还有 PreBell 云端（GitHub Actions cron 推微信）和
叮叮课表单文件 EXE，三端共一份课表数据。

核心指标（全部来自仓库可核对的产物）：
① 连续运行日志 7 天（11-16 至 11-22），共 123 条真实事件，由客户端每天 23:50 自行提交，
   非人工补写。日志含 app_start / reminders_scheduled / system_resume / app_exit 等，
   关机那天就空着，不做假心跳。
② 基于日志的迭代 12 篇，其中 3 篇是发现真实缺陷后改的：010 记录课表为空那三天 77 次
   「已安排 0 条」；011 发现提交文案把「累计 114 条」写成「当日 114 条」，改口径并补单测 9/9；
   012 发现云端 20 次 cron 全部 success 但 0 条消息发出。
③ 源码 123 个文件；课程提醒真实送达 4 次（11-19 大学英语·教学楼621、政治，11-20 数学、体育·文体中心204），
   另有 2 次为功能测试通知，不计入课程提醒。
④ 真实用户反馈 8 份截图，逐字转录，负面意见照收。

最大排障复盘：云端提醒连续 5 天「假绿」。GitHub Actions 显示 20 次 schedule 全 success，
但 process_logs 里 attempted=0、sent=0。归因不是代码错，而是 GitHub 免费 cron 排队延迟
47~155 分钟，脚本的 pick_period() 只在前后 15 分钟内命中，晚到就直接退出且不落盘——
失败被静默吞掉了。改法是让 cron 显式传大节编号，迟到交由脚本判 skipped_late 并如实落盘。
教训：success 不等于做成了事，日志里没有的，就是没发生。

尚未解决的：校历第 1 周周一按 2026-09-07 推算，未取得官方周历，本人无法确认，
已在页面标注为已知前提；云端修复尚未被真实 cron 验证。
```

## 六、我在文案里刻意保留的两处「不好看」

1. **写了「尚未解决」**——校历锚点未核实、云端修复未验证。表单提示原文写着
   「实事求是的写出真实数据与尚未解决的缺陷，反而能获得更高评价」，
   所以这两条主动写出来，没有藏。
2. **没写「已完全修复云端提醒」**——它至今 0 次成功推送，写「已修复」就是造假。
   周一 08:20 才有第一次验证机会，若那时仍为 0，这段表述也不需要改，因为它本来就没说修好了。

**若你想把这两条删掉再提交，我不建议，但决定权在你。** 删掉后文案会更好看，
但和仓库里 `ASSESSMENT.md`、`iterations/012` 的表述会冲突，评委两边一对就露。保持一致更安全。
