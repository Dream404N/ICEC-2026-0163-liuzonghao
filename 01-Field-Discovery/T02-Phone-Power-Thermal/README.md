# 课题 02 · 个人手机多工况发热与掉电实测

> 官网原文：「测试手机在待机、短视频、导航/拍摄、高帧率游戏 4 种工况下 30 分钟内每 5 分钟的电量与发热分布。」
> 交付要求：「提交 24 组时间序列 CSV 表，分析高功耗硬件模块并提出系统省电策略。」
> 前置硬性要求：本校实地采样原始数据表（`raw_data/`）+ 本人现场同框照片。

## 1. 为什么自研采集工具

市面上的电量监控 App（AccuBattery、Battery Guru 等）和系统自带的电池页面都不满足本题，原因很具体：

| 现成工具的短板 | 后果 | 本项目的做法 |
|---|---|---|
| 只输出长期统计（充放电循环、健康度） | 无法按「工况」打标签，4 个场景的数据混在一起 | 每个工况独立会话，CSV 内 `scenario` 列强制标记 |
| 系统页面只给 5 分钟粒度的耗电排行，不能导出原始时序 | 拿不到 t=0/5/10/…/25 的连续序列 | 按绝对时刻调度，落原始 CSV |
| 只显示电量百分比 | 30 分钟内可能只掉 2–3%，分辨率不足以比较工况 | 直读 PMIC 电流（mA），1 分钟内的负载波动都能看见 |
| 不记录「测试期间前台是哪个 App」 | 无法自证「短视频工况真的在刷短视频」，评委只能信你口述 | 每次采样用 `dumpsys` 抓前台包名，与时间戳对齐写入 CSV |

最后一条是这个方案最关键的设计：**它把「工况是否真的执行」从主观陈述变成了可核验的客观记录**。官网反复强调「防摆拍」，这一列就是我的反证。

### root 带来的增量

测试机 Redmi K60 Ultra 已 root（Magisk），因此可以：

- 直接读 `/sys/class/power_supply/battery/current_now`（µA 级瞬时电流），而不是仅靠 `BatteryManager` 的整数百分比；
- 遍历 `/sys/class/thermal/thermal_zone*/`，同时拿到电池温度、SoC 各簇温度、最高热区及其名称——能回答「热在哪」，而不只是「热不热」；
- 用 `dumpsys activity activities` 获取前台包名，作为工况执行证据；
- 用 `dumpsys power` 确认屏幕是否熄灭，区分「待机」是真灭屏还是亮屏放着。

非 root 环境下 App 会自动回退到 `BatteryManager` + `ACTION_BATTERY_CHANGED`，报告里会明确标注 `root 直读 sysfs：失败`，不隐瞒数据来源降级。

## 2. 采集工具

`tools/PowerProbe/`（Kotlin，零第三方依赖，约 1400 行）。

- 4 个工况按钮，每个启动一次 30 分钟 / 6 个采样点的会话
- 前台服务 + `PARTIAL_WAKE_LOCK`，保证灭屏后定时器不被冻结
- 绝对时刻调度（`startAt + seq × 5min`），避免单次采样耗时累积成漂移
- 产物：每个工况一份 CSV + 一份 Markdown 报告，同时复制到 `/sdcard/Download/PowerProbe/`
- APK 由 GitHub Actions 云端构建，产物在 Release `apk-latest`

字段定义与单位归一化规则见 `tools/PowerProbe/README.md`。

## 3. 四个工况的定义与执行规范

严格规范见 [`protocol.md`](./protocol.md)。核心约束：

| 工况 | 代号 | 判定标准（写入 CSV 的前台包名应稳定为） |
|---|---|---|
| 待机 | `IDLE` | 屏幕熄灭、无交互，前台应回到桌面 launcher |
| 短视频 | `SVIDEO` | 抖音/快手连续滑动播放，中途不切后台 |
| 导航/拍摄 | `NAVCAM` | 高德/百度导航持续定位 + 相机录制，二者各占一半时长 |
| 高帧率游戏 | `GAME` | 一款支持高帧率的游戏，画质与帧率设置为最高档 |

**四个工况必须从同一电量起点出发（80%），且相邻两次之间机身冷却到 ≤32℃**，否则第二个工况的起始温度会被上一次污染，温升数据全部失真。这是本课题最容易出错、也最容易被面试追问的地方。

## 5. 数据可信度设计

面试会调 commit 历史追问采样边界，所以这些约束提前写死：

1. **时间戳来自设备系统时钟**，`timestamp_iso` 与 `elapsed_s` 双列并存，任何中途改系统时间的操作都会让两列互相矛盾。
2. **CSV 一旦生成不再手工编辑**，所有修订通过分析脚本完成，脚本本身在版本控制里。
3. **异常点不删除**，在 `analysis/` 的说明里逐条标注（例如某次采样前台包名是系统桌面而不是目标 App，说明中途误触 HOME）。
4. **每个工况的收尾行 `is_final=1`**，其 `elapsed_s` 应接近 1800 秒，用于校验该会话是否被提前中断。
