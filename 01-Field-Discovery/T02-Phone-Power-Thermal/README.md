# 课题 02 · 个人手机多工况发热与掉电实测

> 官网原文：「测试手机在待机、短视频、导航/拍摄、高帧率游戏 4 种工况下 30 分钟内每 5 分钟的电量与发热分布。」
> 交付要求：「提交 24 组时间序列 CSV 表，分析高功耗硬件模块并提出系统省电策略。」
> 前置硬性要求：本校实地采样原始数据表（`raw_data/`）+ 本人现场同框照片。

> **数据状态（2026-11-10）**：真机数据已回传归档，三个工况为完整 7 点序列，
> 相机录像工况录满 34 分钟但只落了 2 个采样点（采集进程被系统挂起）。
> 哪些数据能进结论、哪些只作过程证据、还差什么，全部写在
> [`DATA_QUALITY.md`](./DATA_QUALITY.md)。本课题**尚未 100% 完工**，请勿把残缺样本当完整序列引用。

## 1. 为什么自研采集工具

市面上的电量监控 App（AccuBattery、Battery Guru 等）和系统自带的电池页面都不满足本题，原因很具体：

| 现成工具的短板 | 后果 | 本项目的做法 |
|---|---|---|
| 只输出长期统计（充放电循环、健康度） | 无法按「工况」打标签，4 个场景的数据混在一起 | 每个工况独立会话，CSV 内 `scenario` 列强制标记 |
| 系统页面只给 5 分钟粒度的耗电排行，不能导出原始时序 | 拿不到 t=0/5/10/…/25 的连续序列 | 按绝对时刻调度，落原始 CSV |
| 只显示电量百分比 | 30 分钟内可能只掉 2–3%，分辨率不足以比较工况 | 直读 PMIC 电流（mA），1 分钟内的负载波动都能看见 |
| 不记录「测试期间前台是哪个 App」 | 无法自证「短视频工况真的在刷短视频」，评委只能信你口述 | 每次采样用 `dumpsys` 抓前台包名，与时间戳对齐写入 CSV |

最后一条是这个方案最关键的设计：**它把「工况是否真的执行」从主观陈述变成了可核验的客观记录**。官网反复强调「防摆拍」，这一列就是我的反证。

### 双通道：有 root 用 root，没有也能跑

测试机 Redmi K60 Ultra 已 root（Magisk），所以能用上更细的数据；但工具本身不依赖 root，
两条通道写在同一次采样里，逐点记录来源（CSV 的 `data_source` 列）：

| 通道 | 条件 | 数据 |
|---|---|---|
| A · root 只读直读 | su 可用 | `current_now` 的 µA 级瞬时电流；`thermal_zone*` 全部热区及其名称（能回答「热在哪」，不只是「热不热」）；各核与 GPU 频率；`dumpsys` 的真实前台 Activity |
| B · 公共 API | 无 root 或 su 被拒 | `BatteryManager` 电流与库仑计、粘性广播的电压与温度、`/proc/stat` CPU 占用、`UsageStatsManager` 前台应用 |

这样做的原因：**评审复现时不该要求评委有 root**。有 root 拿细数据，没 root 也能跑出完整时序，
报告里给出每个字段的可用率，不隐瞒降级。

root 的安全边界用代码强制，不是靠承诺：命令不接受任何外部输入、命中
`rm/mkfs/dd/mount/format/wipe/reboot` 等关键词直接拒绝执行、不带设备管理器、不申请网络权限。
逐条可审计清单见 [`tools/PowerProbe/SECURITY.md`](../../tools/PowerProbe/SECURITY.md)。

### 自动化：不是「点一下记一下」

上一版是手动点工况、手动开 App、手动灭屏，本质是个记录器。现在把它做成执行器：

- **工况队列**：一次启动连跑 `IDLE → SVIDEO → NAVCAM → GAME`，每个工况 30 分钟，
  到点自动 `force-stop` 目标 App、自动归档、自动接下一个，全程 2 小时无人值守；
- **自动加压**：待机工况自动发休眠指令并每 2 分钟复核屏幕是否仍熄灭；短视频工况自动拉起
  抖音/快手并每 25 秒上滑翻页；相机录像工况开场即触发录制并全程保活；
- **自动存证**：每个工况开始时与每 10 分钟各截一张图，落在 `Download/PowerProbe/shots/`，
  与 CSV 时间戳对齐，构成「工况确实在执行」的证据链；
- **目标 App 自适应**：首次启动自动探测本机已装的候选（包名会随商店渠道变），
  探测不到让用户从已安装列表里点一个，换机器也能跑。

这里有个自我约束值得单说：**自动化本身会耗电**。如果每分钟跑一次 `dumpsys` 去确认前台应用，
测出来的就是 PowerProbe 的功耗，不是被测 App 的。所以翻页保持 25 秒一次、截图 10 分钟一次，
采样点附近不做任何 shell 调用。

## 2. 采集工具

`tools/PowerProbe/`（Kotlin，约 1900 行；UI 依赖 Material Components，其余全走 Android SDK 原生 API）。

- **一键全自动**：连跑 4 个工况，每工况 30 分钟 / 6 个采样点（对齐官网 24 组口径），
  自动拉起 App、自动灭屏、自动翻页、自动触发相机录像、自动归档
- 前台服务 + `PARTIAL_WAKE_LOCK`，保证灭屏后定时器不被冻结
- 绝对时刻调度（`startAt + seq × 5min`），避免单次采样耗时累积成漂移
- 产物：每个工况一份 CSV + 一份 Markdown 报告，经 MediaStore 导出到 `Download/PowerProbe/`
- APK 由 GitHub Actions 云端构建，产物在 Release `apk-latest`

字段定义、单位归一化规则与安全审计点见 `tools/PowerProbe/README.md` 与 `SECURITY.md`。

## 3. 四个工况的定义与执行规范

严格规范见 [`protocol.md`](./protocol.md)。核心约束：

| 工况 | 代号 | 判定标准（写入 CSV 的前台包名应稳定为） |
|---|---|---|
| 待机 | `IDLE` | 屏幕熄灭、无交互，前台应回到桌面 launcher |
| 短视频 | `SVIDEO` | 抖音/快手连续滑动播放，中途不切后台 |
| 导航 / 拍摄（本机按拍摄执行） | `NAVCAM` | 全程相机录像，前台稳定为系统相机 `com.android.camera`；实测高德深链不生效，故不跑导航半程 |
| 高帧率游戏 | `GAME` | 一款支持高帧率的游戏，画质与帧率设置为最高档 |

**四个工况必须从同一电量起点出发（80%），且相邻两次之间机身冷却到 ≤32℃**，否则第二个工况的起始温度会被上一次污染，温升数据全部失真。这是本课题最容易出错、也最容易被面试追问的地方。

## 5. 数据可信度设计

面试会调 commit 历史追问采样边界，所以这些约束提前写死：

1. **时间戳来自设备系统时钟**，`timestamp_iso` 与 `elapsed_s` 双列并存，任何中途改系统时间的操作都会让两列互相矛盾。
2. **CSV 一旦生成不再手工编辑**，所有修订通过分析脚本完成，脚本本身在版本控制里。
3. **异常点不删除**，在 `analysis/` 的说明里逐条标注（例如某次采样前台包名是系统桌面而不是目标 App，说明中途误触 HOME）。
4. **每个工况的收尾行 `is_final=1`**，其 `elapsed_s` 应接近 1800 秒，用于校验该会话是否被提前中断。
