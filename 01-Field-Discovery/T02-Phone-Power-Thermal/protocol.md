# 课题 02 测试协议 v1

> 目的：让 4 个工况的数据具备**可比性**。工况之间唯一的变量应该是「使用场景」，其余条件全部锁死。
> 违反任何一条前置条件，该次会话作废重测，不通过后期修正弥补。

## 一、前置锁定（每个工况开始前逐项确认）

| 项 | 要求 | 为什么 |
|---|---|---|
| 起始电量 | **80%**，允许偏差 ±2% | 锂电池在不同 SOC 区间的内阻与放电曲线不同，起点不一致则功率不可比 |
| 起始电池温度 | **≤ 32℃** | 温度高会使内阻下降、电流表现虚高，且触发降频 |
| 静置时间 | 充满/回温后**静置 ≥10 分钟**，期间不操作 | 让 SoC 从充电余热中回落 |
| 屏幕亮度 | **手动固定 50%**，关闭自动亮度 | 屏幕是最大耗电件之一，亮度不同会掩盖其他差异 |
| 音量 | 固定 30%，不戴耳机 | 外放功耗与音量线性相关 |
| 移动网络 | 同一张卡、同一位置、**关闭 5G 用 4G** | 5G 射频功耗波动大，跨工况不可比 |
| Wi-Fi / 蓝牙 / NFC | **关闭**（除说明会用到） | 后台扫描会引入非受控功耗 |
| 定位 | **四工况统一关闭** | 相机录像不需要 GPS，关闭可避免额外负载 |
| 后台应用 | 清理一次后台，关闭自动更新与云同步 | 避免其他 App 抢 CPU |
| 充电 | **不插线** | 插线时 `current_now` 为正，数据不可作为放电基线 |
| 机壳 | 不带保护壳，手机平放在**同一张桌面**上 | 散热条件一致；带壳会显著改变温升 |

## 二、四个工况的操作定义

### IDLE · 待机

1. 完成前置锁定，确认电量 80%。
2. 启动 App → 点「待机 30min」。
3. **按电源键灭屏**，手机正面朝上平放桌面，30 分钟内不触碰、不移动。
4. 期间不要给手机充电、不要开热点、不要接收大量通知。

判定：CSV 中 `screen_on` 全程为 0，`foreground_pkg` 应稳定为桌面 launcher 包名。

### SVIDEO · 短视频

1. 前置锁定 + 回温到 ≤32℃。
2. 先打开抖音/快手，**登录并预加载首页**（避免首屏网络请求计入统计）。
3. 回到 App 点「短视频 30min」，**10 秒内切回短视频**并保持前台。
4. 30 分钟内连续下滑播放，**不点赞、不评论、不进直播间**（交互会引入额外 CPU/网络负载）；每 5 分钟滑 2–3 条即可维持播放。
5. 中途不要切后台、不要回消息。

判定：`foreground_pkg` 全程应为同一个短视频包名（如 `com.ss.android.ugc.aweme`）。

### NAVCAM · 相机录像（官网工况「导航 / 拍摄」的拍摄部分）

> **2026-11-10 实测调整**：本机高德深链不生效，运行日志明确留下
> 「非高德地图，跳过深链导航」，真机前台全程是 `com.android.camera`。
> 因此本工况按官网「导航 / 拍摄」中的**拍摄**部分执行，全程相机录像，
> 不再保留跑不起来的导航半程。工况代号 `NAVCAM` 沿用不改，以兼容已采集的 CSV。

1. 保持屏幕常亮，**全程相机录像**（默认系统相机，尽可能高的分辨率/帧率），录制不间断。
2. 定位保持关闭，避免 GPS 成为额外负载；相机录像本身就是 ISP + 编码器的稳定重负载。
3. 室内固定位置即可，机位、环境光尽量跨工况一致。
4. App 在开场自动触发录制，之后只做低频保活，不重复按快门（KEYCODE_CAMERA 是开始/停止切换）。

判定：`foreground_pkg` 全程应为同一个相机包名（本机为 `com.android.camera`）；
若中途变成 `com.icec.powerprobe` 或其他应用，该轮视为无效、需补采。
温度与电流曲线应呈持续高负载平台，不再有「15 分钟拐点」这一预期。

### GAME · 高帧率游戏

1. 前置锁定 + 回温到 ≤32℃（这一轮最容易起始温度超标，务必等够）。
2. 进入游戏设置：**画质最高、帧率最高**（K60 Ultra 支持 120fps 的机型请开到最高档），关闭省电模式。
3. 回到 App 点「高帧率游戏 30min」，10 秒内切回游戏。
4. 30 分钟内保持同一场景（建议训练场/人机局），避免不同地图负载差异。
5. 不要中途调画质、不要切后台。

判定：`foreground_pkg` 为游戏包名，`gpu_mhz` 与 `cpu_load_pct` 应显著高于其他三个工况。

## 二·附、自动化执行（可替代上述手动步骤）

App 提供两种「一键全自动」模式，作用是把上面每个工况里的**动作**交给程序：

| 模式 | 工况间隔 | 用途 |
|---|---|---|
| 合规 | 30 分钟冷却窗口 | **正式交付数据**用这个。窗口内只需插线充到 80% 再拔线，计时结束自动开始下一工况 |
| 连续 | 无间隔 | 流程验证 / 连续负载梯度实验。**数据不带冷却复位，不能当 protocol 口径交付** |

自动化具体做什么：

- 待机：自动发休眠指令灭屏，每 2 分钟复核屏幕仍熄灭（被点亮会再灭一次）
- 短视频：自动拉起目标 App，每 25 秒上滑翻页
- 相机录像：开场自动拉起系统相机并触发录制，全程低频保活（不再中途切换）
- 游戏：自动拉起游戏并保持前台（游戏内操作不注入，避免违规）
- 每个工况开始与每 10 分钟各 `screencap` 一张存证，落到 `Download/PowerProbe/shots/`
- 每个工况结束自动 `force-stop` 目标 App、归档 CSV 与报告、接下一个工况

仍需人工完成、无法自动化的只剩三件：**充电拔线、设置画质/帧率、现场同框照**。
这三件都属于物理动作或账号相关设置，不是软件能替代的。

无 root 时自动化降级为「只自动拉起 App + 采样」，灭屏/翻页/切相机需手动，
App 会在日志与报告里标注当前通道，不影响数据可用性。

## 三、工况之间的复位流程

每轮结束到下一轮开始，必须走完：

1. 记录本轮结束时的电池温度（App 报告里已有）。
2. 插线充电回 80%——**注意充电会加热**，充完必须拔线。
3. 拔线后静置，直到电池温度 **≤32℃**（通常 15–25 分钟，游戏轮可能更久）。
4. 重复「一、前置锁定」逐项确认。
5. 开始下一轮。

**顺序固定为 IDLE → SVIDEO → NAVCAM → GAME**，功耗递增，最热的一轮放最后，避免污染前面的基线。

## 四、作废重测的条件

出现任一条即作废，不修补：

- 起始电量偏离 80% 超过 ±3%
- 起始电池温度 > 33℃
- 30 分钟内采样点缺失 ≥2 个（CSV 中正式行 <5）
- `foreground_pkg` 与目标工况不符（中途误触 HOME、被通知打断）
- 检测到充电（`charging=1`）
- 屏幕状态与工况定义不符（待机未灭屏 / 其他工况中途灭屏）

## 五、现场同框照片

每个工况至少 **1 张**，存 `photos/`，命名 `T02_<SCENARIO>_<序号>.jpg`。

照片必须同时包含：

1. 本人（至少半身或清晰正脸）
2. 测试机屏幕（能看到 App 正在采集的状态）
3. 场景可辨识要素（宿舍桌面 / 食堂 / 户外街道 / 游戏画面）

拍摄方式：用另一台设备或请同学帮拍，**不要只用手机自拍**——自拍无法同时拍到屏幕状态和场景。若只有一台设备，用镜子/玻璃反光，并在 README 里说明拍摄方式。

另补 1 张设备信息页（设置 → 关于手机，显示型号与系统版本），以及 App 内「权限与数据源」卡片
（显示 root 通道是否已授权、使用情况访问是否已授予、当前数据来源），
两张都存 `photos/`，命名 `device_info.jpg` 与 `data_source.jpg`——这是文档里「双通道」说法的直接证据。

## 六、执行排期

单轮净耗时约 60–70 分钟（采集 30 + 冷却 15 + 充电 10 + 静置 10），四轮合计约 4.5 小时。

建议拆两天，避免深夜做「游戏」轮时起始温度压不下来：

- **D1 晚**：IDLE + SVIDEO
- **D2 晚**：NAVCAM + GAME

每天做完立即把 CSV 从 `/sdcard/Download/PowerProbe/` 取到 `raw_data/` 并 commit，不要攒到最后——官网明确要求「每日同步」。
